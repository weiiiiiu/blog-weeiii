> 项目原文：[DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)

一家 SaaS 公司收到工单：“我们已经付款，为什么还是免费版？”客服通常要查订单、核对账号、看开通任务、翻处理规程，再找有权限的同事补处理。DeepSeek Harness 可以作为这段工作的执行框架：让模型根据任务选择已接好的工具，逐步获取证据，形成处理建议；在获得必要授权后，还可以调用业务操作并检查结果。

它的企业用途由**模型、已接入的工具、业务规则和权限范围**共同决定。仅安装 Harness，并不会自动获得公司的订单、数据库或工单访问权。下面不展开内部代码，而是讲清楚一件事怎样从“提出要求”走到“确认完成”。

本文以 `@deepseek-ai/dsh` **0.2.2-rc.5** 为说明范围。官方仍将其标记为开发者预览，并明确不能视作生产就绪软件。因此，这里展示的是可搭建的企业流程与受控试点方法，不是项目已经提供的一套成品客服系统。[官方说明](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/README.zh.md)、[项目安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/SAFETY.zh.md)

## 它在企业工作中负责哪一段

先把参与者分开，就容易理解它的作用。

| 参与者 | 负责的工作 | 工单中的例子 |
| --- | --- | --- |
| 业务人员 | 提出目标、补充信息、确认需要人负责的决定 | “帮我核查这张工单，先别改权限” |
| 大模型 | 理解任务，选择下一步查询，结合结果组织判断 | 发现订单已付，但还缺当前权限状态，于是继续查权限 |
| Harness | 把任务、上下文、工具调用和返回结果组织成连续执行过程 | 把查询请求交给工具，把结果带入下一轮模型判断 |
| 企业工具或连接器 | 将一项明确能力暴露给智能体，并连接对应系统 | “按订单号查询支付状态”“查询开通任务” |
| 企业业务系统 | 保存权威数据，执行真正的业务变更 | 订单服务记录付款，权限服务授予套餐权益 |

**真正让套餐开通的是企业的权限服务。** 模型提出应该调用什么能力，Harness 负责组织调用，工具负责把请求送到业务系统。没有开通接口，就不能靠一段回答把服务变成已开通。

“工具”在这里不是一个模糊的外挂。它是一张明确的能力卡片：叫什么、需要哪些输入、能返回什么、是否会改变业务状态。例如：

> 能力：查询订单。输入：订单编号。返回：所属账号、产品、付款状态、退款状态和数据时间。权限：只读。

Harness 支持通过插件和 MCP 接入外部工具。MCP 可以理解成让智能体调用外部能力的一种通用连接方式；企业仍需要提供真正查订单、查权限或执行补开通的服务。默认安装不会替企业创建这些系统。[MCP 接入说明](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/mcp/mcp-client/README.zh.md)

## 一项任务怎样一步步得到结果

![DeepSeek Harness 任务执行流程，模型根据可用工具选择动作，Harness 调用工具，返回结果再参与下一轮判断](/imgs/learning-notes/deepseek-harness-task-loop.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-task-loop.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-task-loop.mmd)

这个过程可以分成七步：

1. **收到目标。** 用户输入工单编号和要求，例如只核查、生成回复草稿，暂不修改任何业务数据。
2. **准备本轮上下文。** Harness 把任务、已有对话、业务约束以及可用工具的说明交给模型。此前查过的结果也会影响后续判断。
3. **模型选择下一步。** 模型可能提出调用工具，也可能要求补充必要信息，或者认为证据已经足够，直接组织答案。
4. **Harness 把工具请求交给执行环节。** 根据实际配置检查调用条件和权限；需要审批的操作进入相应审批流程。企业工具还必须自行做账号、租户和业务校验。
5. **工具访问企业系统。** 查询或操作由接口实际完成，返回数据、错误，或一个仍在处理中的任务编号。
6. **模型读取结果，再决定下一步。** 查到“已付款”并不能结束任务，因为它还不知道“是否开通”；查到“开通失败”也不能立即宣布原因已确定，还要核对时间、当前状态和处理规则。
7. **形成答案或进入下一轮。** 直到达到约定的完成条件，或者因为信息不足、权限不足、接口错误、取消等原因停止。

所以，一次业务任务通常会包含多次“判断 → 调用 → 观察结果”。模型不是一开始就知道后面所有步骤，它会受到每次查询结果的影响。Harness 提供的是这个连续执行过程及相关会话、工具和记录能力。[架构与任务流](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/docs/architecture.zh.md)

这种灵活性也意味着：如果公司要求每次必须核对支付、退款和租户，不能只期待模型“记得去查”。决定能否真正补开通的关键条件，应在业务接口中再次强制校验。

## 处理工单前公司需要接好哪些能力

下面是这个企业场景的能力设计，不是 Harness 默认自带的工具名称。

| 业务能力 | 输入是什么 | 输出要有什么 | 为什么需要 |
| --- | --- | --- | --- |
| 读取工单 | 工单编号 | 客户描述、订单号、账号、产品、来源 | 确定查的是哪一件事 |
| 查询订单 | 订单号及受控身份上下文 | 支付、退款、归属、付款时间 | 核实是否真的满足开通前提 |
| 查询当前权益 | 账号、产品 | 当前套餐、权益状态、更新时间 | 确认此刻是否仍未生效 |
| 查询开通任务与事件 | 订单或关联任务号 | 回调、任务状态、失败记录、在途任务 | 找到流程卡在哪一段 |
| 查询处理规程 | 产品及问题类型 | 等待窗口、可处理条件、审批角色 | 避免凭感觉补开通 |
| 提交补开通请求 | 已核验的业务对象与审批凭据 | 接受或拒绝、任务编号、去重结果 | 在允许的范围内发起真实处理 |
| 写回工单或发送消息 | 经过确认的结论与内容 | 写回记录或发送结果 | 将处理结果交给实际业务流程 |

最后两项可以先不接。第一阶段只提供查询能力，让它生成证据完整的核查报告，通常已经能够减少客服反复切换多个后台的工作。

企业工具的访问身份应来自已经认证的员工或受限服务账号。不能让模型随口填一个 `tenant_id`，就因此获得那个租户的数据权限。工具输入是查询条件，后端鉴权才决定能不能查。

公司也不必一次开放完整数据库。可以先提供几项范围明确的查询：只返回处理工单所需字段，保留业务记录编号和数据时间。这样模型获得的是足够作出判断的证据，而不是一个需要自由探索的全部生产环境。

## 先走完已付款但未开通的核查过程

以下是一组**完全虚构的演示数据**。观察时点固定为 **2026-11-21 16:18 UTC**；五分钟等待窗口也是本例的业务约定。

工单 `TK-1001` 对应：租户 `DEMO-CORP`、账号 `ACCT-017`、订单 `ORD-10086`、产品 `TEAM-5`。用户说已付款，但页面仍显示免费版。

### 第一步 把模糊描述变成明确查询对象

客服输入：

> 核查 TK-1001 的付款和开通情况。请检查订单、账号权益、开通记录和处理规程。输出证据与下一步建议，先不要执行补开通或发送回复。

Harness 将任务送给模型，模型提出读取工单。工具返回关联标识后，后续查询才有了范围。

如果工单里没有订单号，且同一账号有多笔订单，正确动作是查询候选记录并请业务人员确认。不能自行挑一笔金额接近的订单继续处理。

### 第二步 核实付款和业务归属

订单查询返回：

| 字段 | 演示结果 |
| --- | --- |
| 订单 | `ORD-10086` |
| 所属账号与产品 | `ACCT-017` / `TEAM-5` |
| 支付状态 | `PAID`，已支付 |
| 退款状态 | 未退款 |
| 付款时间 | 16:02 UTC |
| 证据位置 | `orders:ORD-10086` |

这一步证明的是“该订单满足已付款条件”。客户提供的截图、工单标题或模型自己的判断都不能替代订单系统记录。实际接入时，如果订单系统与支付渠道记录冲突，需要走公司的对账处理流程。

### 第三步 查询当前权益

权限查询显示：`ACCT-017` 的 `TEAM-5` 权益为 `INACTIVE`，当前套餐仍是 `FREE`，数据观察时点是 16:18 UTC。

至此，可以确认“付款记录存在，但截至这个时点，对应权益仍未生效”。这一步必须查当前状态，因为十分钟前的一条失败日志，不代表系统后来没有重试成功。

还要匹配同一个账号和产品。本例另一个账号 `ACCT-018` 已开通，不能把它的成功记录用来证明 `ACCT-017` 正常。

### 第四步 沿时间线找到中断的位置

模型继续请求开通事件和任务状态，得到：

| 时间 | 业务事件 | 能说明什么 |
| --- | --- | --- |
| 16:02:00 | 订单记录支付成功 | 付款这一环已经有成功记录 |
| 16:02:03 | 支付回调已收到 | 不能再笼统归因为“支付消息没来” |
| 16:02:04 | 开通任务 `JOB-5002` 开始执行 | 流程已经进入开通环节 |
| 16:02:34 | 调用权限服务超时，任务失败 | 这次开通调用没有得到成功确认 |
| 16:18:00 | 当前权益未生效、该订单在途任务数为零 | 尚无当前生效或正在处理的证据 |

这些结果把问题从“可能哪里都出错了”缩小为“支付回调之后的开通链路需要处理”。但它们还不能证明唯一根因，例如网络问题、下游繁忙、响应丢失，都可能表现为超时。

因此，报告应把**已确认的中断位置**与**仍待排查的底层原因**分开。不能把一次超时直接写成“权限数据库损坏”。

### 第五步 对照业务规程决定下一步

演示规程 `RB-ENT-001` 规定：正常等待窗口为付款后五分钟；提出补开通建议前，需确认已付款未退款、权益未生效、没有在途任务，并由授权人员审批。

从 16:02 到 16:18 已经过了 16 分钟。结合现有数据，这张工单可以提出补开通建议，但“可以建议”不等于“已经得到执行授权”。

### 第六步 给客服一份能核对的结果

合适的核查输出大致如下：

> **结论：** 截至 16:18 UTC，ORD-10086 已支付且未退款，ACCT-017 的 TEAM-5 权益尚未生效。
>
> **中断位置：** 支付回调已收到，最近一次开通任务 JOB-5002 调用权限服务超时，当前没有在途开通任务。
>
> **证据：** orders:ORD-10086、entitlements:ACCT-017:TEAM-5、jobs:JOB-5002、events:EV-002、events:EV-004。
>
> **建议：** 按 RB-ENT-001 提交补开通审批；执行前再次检查订单、退款、权益与在途任务。
>
> **当前未完成：** 尚未执行补开通，未证明根因已经消除，也未发送客户通知。

客服回复草稿可以写：“已核实付款记录，当前套餐权益尚未生效，问题出现在后续开通环节，我们正在按流程处理。”没有实际恢复证据时，不应写“已经为您开通”，也不要编造恢复时间。

## 获得授权后怎样实现真正补开通

下面的时序图展示**接入企业查询与写入工具后的一条成功路径**。上一节的模拟资料只覆盖核查阶段，没有真的执行这些业务变更。

![付款未开通的处理时序，从查询工单和订单，到审批补开通，再查询实际权益并确认业务结果](/imgs/learning-notes/deepseek-harness-ticket-sequence.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-ticket-sequence.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-ticket-sequence.mmd)

补开通阶段有五个关键动作。

**第一，明确批准的是哪一个动作。** 审批内容应包含订单、账号、产品、准备执行的操作和必要证据。“看一下这张工单”不是“修改客户权限”的同义词。Harness 的工具审批可以参与这一步，但企业审批人资格和业务审批凭据仍需企业系统管理。[工具审批能力](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/interaction/user-approval/README.zh.md)

**第二，执行前重查关键状态。** 核查之后，后台可能已经自动补成功，或者订单刚刚退款。真正的补开通接口必须再次核验，不能无条件使用几分钟前的结论。

**第三，让业务接口防止重复执行。** 同一张工单可能被重复点击，网络超时也可能导致再次提交。企业接口需要根据稳定的业务操作标识识别重复请求，使同一笔应开通的权益不会重复发放。这个保障属于业务服务，不应依赖模型承诺“我只调用一次”。

**第四，区分受理与完成。** 接口可能只返回“请求已受理”和任务编号。此时 Harness 能知道任务已经提交，但还不知道权限是否生效。它需要调用查询能力继续观察；长时间任务则由企业任务系统保存状态并负责后续唤醒，不应把可靠性押在一次聊天进程一直在线上。

**第五，查询实际业务结果。** 只有当正确账号、正确产品的权益已经生效，才满足“补开通成功”的业务条件。若用户仍无法使用，还要继续检查登录账号、登录态或其他相关访问条件。随后按照授权范围写回工单、发送回复；这些也是独立操作，需要各自的成功结果。

也就是说，过程中的几种“成功”有不同含义：

| 看到的结果 | 能确认的事情 | 还不能确认的事情 |
| --- | --- | --- |
| 模型说“准备补开通” | 已提出动作 | 尚未调用业务系统 |
| 工具调用没有报错 | 这一轮工具返回了结果 | 返回内容可能只是已受理 |
| 开通任务已创建 | 后台会尝试处理 | 权益未必已经生效 |
| 权益查询显示生效 | 业务对象达到预期状态 | 客户通知、工单关闭可能还没做 |
| 通知和工单写回也成功 | 约定的业务处理已完成 | 仍应保留证据和操作记录 |

Harness 最终能帮助实现结果，靠的是**调用真正能办事的系统，并用再次查询验证结果**，而不是让模型把一句话说得更肯定。

## 查询结果不同后续路线也不同

![工单处理分支图，区分付款不成立、权益已生效、正常等待、待核查、审批补开通和结果复查](/imgs/learning-notes/deepseek-harness-ticket-branches.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-ticket-branches.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-ticket-branches.mmd)

同一句“已付款未开通”，可能对应不同问题：

| 查到的情况 | 应走的路线 | 不能做的事 |
| --- | --- | --- |
| 订单未支付、已退款或关联不一致 | 核对支付与订单归属，必要时转对应人员 | 直接给予付费权益 |
| 权益已经生效 | 核对使用账号、产品入口或登录状态 | 再执行一次开通 |
| 仍在正常等待窗口，或已有任务运行 | 返回当前状态，按规程等待与复查 | 不断提交重复任务 |
| 超出窗口，任务失败且可按规程补处理 | 收集证据，进入审批与补开通流程 | 把建议当成授权 |
| 接口超时或关键数据缺失 | 标记无法核实，重查或升级处理 | 把“没查到”写成“肯定没有” |
| 同一服务大量订单同时异常 | 关联故障事件，交给故障处理流程 | 单靠逐单重试放大故障 |

这也是它相较于一条固定脚本可能有价值的地方：输入描述、涉及系统和异常分支不总相同，模型能够结合工具结果组织后续调查。

但如果业务流程始终是固定的几个条件，现有工作流、定时任务或补偿机制通常更直接。比如“付款后五分钟仍未开通则触发幂等补偿”，本来就可以由确定性业务系统处理。Harness 更适合辅助解释异常、汇总跨系统证据、处理长尾分支；不应因为加入了 AI，就把原有可靠补偿机制拆掉。

## 不接真实系统也能先体验一次

我准备了一份[模拟工单资料包](/examples/deepseek-harness-ticket-demo.zip)，包含五份 CSV、处理规程、任务文本和说明文件。所有记录都是虚构的，解压后没有需要运行的业务程序。

| 文件 | 代表的企业资料 |
| --- | --- |
| `tickets.csv` | 工单及关联的账号、订单、产品 |
| `orders.csv` | 支付与退款状态 |
| `entitlements.csv` | 当前权益，包含另一账号作为关联检查项 |
| `activation_jobs.csv` | 开通任务、失败状态和在途任务数量 |
| `activation_events.csv` | 支付回调到开通调用的时间线 |
| `runbook.md` | 这次模拟使用的业务规程 |
| `task.txt` | 可以直接粘贴到会话中的任务 |

### 第一步 启动界面

安装 Node.js **24.9.0 或以上**，解压资料包，在解压后的 `deepseek-harness-ticket-demo` 目录打开终端，运行：

```bash
node --version
npx @deepseek-ai/dsh@0.2.2-rc.5 web
```

这里固定版本，避免教程步骤随着开发者预览版变化而混淆。默认 Web UI 使用本机 3080 端口，启动后按终端给出的地址进入；不需要自动打开浏览器时可加 `--no-open`。启动地址可能携带用于访问该进程的凭据，不要当成公开分享链接。[运行方式](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/README.zh.md)、[版本与环境要求](https://www.npmjs.com/package/@deepseek-ai/dsh/v/0.2.2-rc.5)

### 第二步 配置模型并选择资料目录

首次启动若出现预览说明，阅读后继续。在 **设置 → 模型** 配置可用的 DeepSeek API 密钥；也可以按官方模型指南接入公司的兼容模型服务。然后在工作区入口添加并选中解压后的资料目录，再创建会话。界面布局会随版本调整；即便看见默认工作区，也要确认实际选中的是这份资料，而不是其他项目目录。[Web UI 指南](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/docs/user/guide/index.zh.md)、[模型配置](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/docs/user/guide/providers.zh.md)

### 第三步 提交明确的任务

把 `task.txt` 的内容粘贴进去。任务要求按资料的观察时点判断，关联同一个租户、账号、订单和产品，逐项引用证据，并且只输出核查结论和回复草稿。

你应观察到模型确实请求读取相关文件，而不只是根据“已付款未开通”这几个字直接生成通用建议。在这个练习中，文件读取工具承担了数据入口的作用。

### 第四步 检查输出是否建立在资料之上

结果应能确认三件事：ORD-10086 已支付未退款；ACCT-017 的对应权益仍未生效；最近开通任务超时且观察时点没有在途任务。处理建议应符合模拟规程，也应指出尚未执行补开通。

如果它引用 ACCT-018 的成功状态来宣布工单已解决，说明关联有误。如果它说“已经修好”，却没有任何写入工具和后续查询记录，说明它超出了证据。

**这个练习体验的是多份资料的关联、核查与建议。** 要变成实时企业流程，需要把文件入口换成已经接好的业务查询工具，并按需要增加审批后的写入能力；资料包自身没有连接 CRM、支付或权限系统。

## 从人工查询过渡到企业自动处理

在真实企业里，入口可以逐步变化，后面的业务判断方法仍然相似。

**第一阶段，人工发起只读核查。** 客服在界面输入工单编号，Harness 查询已接入的系统，生成报告。客服决定是否采用建议。这一阶段先确认关联准确性、证据完整性和节省了哪些操作。

**第二阶段，接入业务事件。** 新工单到达后，工单系统或企业任务服务创建一次处理任务，把可信身份与工单编号传给 Harness。可通过一次性命令模式或 SDK 等入口驱动任务，不必要求客服一直打开网页。这属于企业接入工作，不是安装后自动出现的功能。[CLI 运行模式](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/apps/cli/README.zh.md)

**第三阶段，加入批准后的操作。** 让报告关联到正式审批；批准后再调用补开通接口。审批被拒绝就停止写入，不能另找一条工具路径绕过。

**第四阶段，才考虑有限自动执行。** 只把范围明确、后果可控、重复执行可防护、结果可验证的动作交给规则授权。出现身份不匹配、数据矛盾、未知错误或超出授权时，应回到人工处理。

企业任务系统还要保存“待查询、待审批、已提交、待复查、已完成、需人工”等状态。进程结束不应丢失工单；重复事件不应创建重复业务操作。会话记录帮助回看智能体做了什么，但订单和工单的最终状态仍应以业务系统为准。

项目的 headless 模式可以输出任务事件，并在单次处理结束后退出。其正常结束表示智能体运行完成，不能直接代替业务验收。例如模型正确回答“缺少权限，无法补开通”，这轮交流可以完成，但工单仍然没有解决。[headless 结果语义](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/bundle/headless/README.zh.md)

## 同一套流程怎样迁移到其他场景

可以保留这条业务链：**收到请求 → 确认对象 → 查询事实 → 对照规则 → 提出或执行动作 → 验证结果 → 留下记录。** 变化的是查询什么、允许做什么，以及什么状态算完成。

| 企业场景 | 要查询的事实 | 可以形成的结果 | 真正完成的判据 |
| --- | --- | --- | --- |
| 员工申请系统权限 | 员工身份、岗位、已有权限、审批规则 | 汇总权限差异，审批后发起授权 | 正确员工得到批准范围内的权限 |
| 客户说已发货但查不到物流 | 订单、仓库出库、运单、承运商轨迹 | 定位未揽收、信息延迟或关联错误，生成处理建议 | 物流状态或异常处理有可核验记录 |
| 研发构建失败 | 失败日志、最近变更、依赖、测试结果 | 解释故障，生成待审阅修复或变更建议 | 约定测试通过，变更经审阅并按流程合入 |
| 采购到货数量不一致 | 采购单、收货记录、仓库盘点、供应商回执 | 生成差异报告和待确认处理单 | 差异经业务确认，相关记录完成一致更新 |
| 客户投诉同类故障 | 多张工单、服务状态、已知故障与处理规程 | 聚合同类问题，关联故障事件并起草统一回复 | 关联准确，通知与恢复状态有证据 |

以员工权限申请为例，不能把“模型认为这个员工应该有权限”作为授权依据。模型可以帮助解释申请和查找规则，正式授权仍取决于企业身份、审批和权限系统。这个责任划分与补开通完全相同。

适合采用这种方式的任务，往往需要跨几个系统查询，输入不完全统一，且结果可以通过已有系统验证。纯粹固定的计算、单条件判断，或没有可靠数据入口的请求，不一定值得引入一整套智能体流程。

## 企业试点时需要看哪些实际指标

先选一类重复出现的工单，用一批已知处理结果的历史样本进行核查，再决定是否扩大范围。不要只看回答是否流畅。

| 指标 | 怎样判断 |
| --- | --- |
| 业务对象是否正确 | 是否关联到正确的租户、账号、订单和产品 |
| 结论能否追溯 | 每个关键事实是否有对应查询结果与时间 |
| 无法核实时是否停止 | 接口失败、资料不足时是否明确升级，而非编造 |
| 是否减少人工操作 | 比较原来的查后台、复制资料和整理回复所用时间 |
| 是否发生越权或重复动作 | 结合业务接口与审计记录检查，不能只看回答 |
| 端到端处理成本 | 综合模型调用、接口查询、运行环境和人工复核成本 |
| 业务闭环是否成立 | 权益实际生效，而非仅仅生成了一个任务编号 |

还需要核对数据传递范围：本机安装 Harness，不等于企业数据只留在本机。进入模型上下文的工单内容和工具结果，会发往所配置的模型端点。应先确定哪些字段允许进入模型、是否使用企业网关，以及如何限制返回数据。

在本文核对的版本中，官方还说明了额外的会话日志上传与反馈相关遥测路径。使用企业资料前，应检查 Web 设置中的官方模型会话日志上传选项，并分别核对部署的遥测设置；其中一个开关不能代表所有数据传递都被关闭。[官方数据与部署默认行为](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/apps/cli/reference/README.md#shared-deployment-behavior)

对于这个工单场景，可以从一个很具体的目标开始：让客服输入工单号，就得到一份对象准确、证据完整、建议清楚的核查报告。验证这一步有价值后，再接审批与补开通。这样每增加一项能力，都能说明它减少了哪一段人工工作，以及通过什么业务结果证明它做对了。
