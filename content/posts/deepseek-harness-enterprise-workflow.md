## 一句话：它是干嘛的

客户说“付了钱，怎么还是免费版”，客服要查订单、查账号、查开通记录，再找人补处理。DeepSeek Harness 就是帮客服跑这段活的框架：模型负责想“下一步查什么”，Harness 负责调工具去查，查完把结果带回来再想下一步。

分工先搞清：

- **模型**只动脑，不办事。它提议查什么、怎么做判断。
- **Harness**只跑腿。它把任务、工具调用和返回结果串成一趟连续的活。
- **工具**是公司接好的能力，比如“按订单号查支付状态”。没接就查不了。
- **业务系统**说了算。真正开通套餐的是公司的权限服务，不是模型一句话。

所以光装个 Harness 什么也干不了，公司的订单、数据库、工单都得先接进来。

版本注意：本文按 `@deepseek-ai/dsh` **0.2.2-rc.5** 写，官方标的是开发者预览，明确说了不能当生产软件用。这里讲的是能搭起来的流程和试点方法，不是一套现成的客服系统。[官方说明](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/README.zh.md)、[项目安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/SAFETY.zh.md)

## 公司要先接好哪些能力

这些不是 Harness 自带的，是公司要提供的查询和操作：

- **读工单**：给工单号，返回客户描述、订单号、账号、产品。
- **查订单**：给订单号，返回支付、退款、归属、付款时间。
- **查权益**：给账号和产品，返回当前套餐、权益状态。
- **查开通任务和事件**：返回回调、任务状态、失败记录、在途任务。
- **查规程**：给产品和问题类型，返回等待窗口、处理条件、审批角色。
- **补开通、写回工单**：先不接也行。第一阶段只做查询、出报告，就已经能省不少事。

工具的访问身份来自已认证的员工或受限服务账号，不能让模型随便填个 `tenant_id` 就拿到那个租户的数据。先给范围明确的几项查询，只返回办工单需要的字段。

## 任务是怎么跑起来的

![DeepSeek Harness 任务执行流程，模型根据可用工具选择动作，Harness 调用工具，返回结果再参与下一轮判断](/imgs/learning-notes/deepseek-harness-task-loop.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-task-loop.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-task-loop.mmd)

一趟任务通常是这样循环的：

1. **接任务。** 比如“核查 TK-1001，只查不改”。
2. **模型看手头有什么。** Harness 把任务、已有结果、能用的工具清单交给模型。
3. **模型挑下一步。** 查个东西、问人要信息，或者觉得证据够了直接给答案。
4. **Harness 调工具。** 按配置检查权限，需要审批的先进审批。
5. **工具真去查。** 返回数据、报错，或者一个“还在处理”的任务号。
6. **模型看结果再决定。** 查到“已付款”不等于完事，还得查“开通了没有”。
7. **够了就收尾，不够就再跑一轮。** 直到达到约定的完成条件，或者因为没权限、没信息停下来。

关键就一句：**模型不是一开始就知道全部步骤，它是查一步、看一步、再定下一步。** 所以公司如果要求“每次必须核对支付、退款和租户”，不能指望模型记得，得在业务接口里强制再验一遍。

## 走一遍：已付款但未开通

下面全是虚构的演示数据，观察时点固定在 **2026-11-21 16:18 UTC**。

工单 `TK-1001`：租户 `DEMO-CORP`、账号 `ACCT-017`、订单 `ORD-10086`、产品 `TEAM-5`。用户说付了钱，页面还是免费版。

**1. 先把工单变成能查的东西。** 客服输入：“核查 TK-1001 的付款和开通情况，只查不改。”模型先读工单，拿到订单号，查询才有范围。工单里没订单号、同一账号有多笔订单时，要列出候选请人确认，不能自己挑一笔金额像的就往下走。

**2. 查订单：到底付没付。** 结果：`ORD-10086` 已支付（16:02 UTC）、未退款，归属 `ACCT-017` / `TEAM-5`。这一步只证明“满足已付款条件”，客户截图、工单标题都不能代替订单系统记录。

**3. 查权益：现在到底开通没。** 结果：`ACCT-017` 的 `TEAM-5` 权益是 `INACTIVE`，还是免费版。必须查当前状态，十分钟前的一条失败日志不代表后来没重试成功。还要注意别拿错账号：`ACCT-018` 开通了，不代表 `ACCT-017` 没问题。

**4. 沿时间线找断在哪。**

| 时间 | 发生了什么 |
| --- | --- |
| 16:02:00 | 订单支付成功 |
| 16:02:03 | 支付回调已收到 |
| 16:02:04 | 开通任务 `JOB-5002` 开始 |
| 16:02:34 | 调权限服务超时，任务失败 |
| 16:18:00 | 权益仍未生效，也没有在途任务 |

结论：问题卡在“支付回调之后的开通环节”。但这只能说明断在哪，不能证明根因，网络问题、下游繁忙、响应丢了都会表现为超时。**不要把一次超时写成“权限数据库损坏”。**

**5. 对照规程，看能不能建议补开通。** 规程 `RB-ENT-001`：付款后等 5 分钟；建议补开通前要确认已付款未退款、权益未生效、没有在途任务，还要有人审批。16:02 到 16:18 已经过了 16 分钟，可以提建议了。但“可以建议”不等于“已经批准执行”。

**6. 给客服一份能核对的报告。**

> **结论：** 截至 16:18 UTC，ORD-10086 已支付未退款，ACCT-017 的 TEAM-5 权益尚未生效。
>
> **断在哪：** 支付回调已收到，最近一次开通任务 JOB-5002 调权限服务超时，现在没有在途任务。
>
> **证据：** orders:ORD-10086、entitlements:ACCT-017:TEAM-5、jobs:JOB-5002、events:EV-002、events:EV-004。
>
> **建议：** 按 RB-ENT-001 提交补开通审批；执行前再查一次订单、退款、权益和在途任务。
>
> **还没做的事：** 没执行补开通，没证明根因，没发客户通知。

给客户的回复可以写：“已核实付款记录，当前套餐权益尚未生效，问题出在后续开通环节，正在按流程处理。”没真恢复之前，别写“已经为您开通”，也别编一个恢复时间。

## 批了之后，怎么真把开通做完

![付款未开通的处理时序，从查询工单和订单，到审批补开通，再查询实际权益并确认业务结果](/imgs/learning-notes/deepseek-harness-ticket-sequence.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-ticket-sequence.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-ticket-sequence.mmd)

上面那段只做到“核查”，真要开通还有五件事：

1. **批的是哪个动作，要写清楚。** 订单、账号、产品、要执行的操作、证据都得在审批里。“看一下这张工单”不等于“改客户权限”。
2. **动手前再查一遍。** 核查完这几分钟里，后台可能已经自动补成功了，或者订单刚退款。不能拿几分钟前的结论直接动手。
3. **接口自己要防重复。** 同一张工单可能被点两次，网络超时也可能导致重提。业务接口要按固定标识去重，不能靠模型保证“我只调一次”。
4. **“受理了”不等于“办完了”。** 接口返回任务编号只是说收到了，还得继续查权益到底生效没有。长时间任务由企业任务系统跟进，别指望一次聊天一直开着。
5. **最后查业务结果。** 只有正确账号、正确产品的权益真的生效了，才算补开通成功。再按授权写回工单、发通知。

## 查到的结果不一样，走法也不一样

![工单处理分支图，区分付款不成立、权益已生效、正常等待、待核查、审批补开通和结果复查](/imgs/learning-notes/deepseek-harness-ticket-branches.svg)

[查看大图](/imgs/learning-notes/deepseek-harness-ticket-branches.svg) · [Mermaid 源码](/diagrams/learning-notes/deepseek-harness-ticket-branches.mmd)

- 订单没付、退了款、归属对不上：先核对支付和归属，绝不能直接给权益。
- 权益其实已经生效了：查账号、产品入口或登录状态，别再开一次。
- 还在 5 分钟等待窗口里，或已有任务在跑：告诉客户当前状态，等着复查，别重复提交。
- 超了窗口、任务失败、能按规程补处理：收证据、走审批、补开通。建议不是授权。
- 接口超时、关键数据查不到：标成“无法核实”，重查或升级。**“没查到”不能写成“肯定没有”。**
- 同一服务大量订单同时出问题：关联故障事件走故障流程，别逐单重试把故障放大。

如果流程永远是固定的几个条件，定时任务或补偿机制更直接，比如“付款后 5 分钟未开通就触发幂等补偿”。Harness 适合的是：跨几个系统查证据、解释异常、处理那些不常见的分支。

## 自己动手试一次

我准备了一份[模拟工单资料包](/examples/deepseek-harness-ticket-demo.zip)，五份 CSV、处理规程、任务文本和说明，全是虚构数据，解压后不用跑任何业务程序。

装 Node.js **24.9.0 或以上**，解压后进 `deepseek-harness-ticket-demo` 目录：

```bash
node --version
npx @deepseek-ai/dsh@0.2.2-rc.5 web
```

默认 Web UI 在本机 3080 端口，按终端给的地址进。启动地址可能带访问凭据，别当公开链接分享。

然后在**设置 → 模型**配 DeepSeek API 密钥（或公司的兼容模型服务），工作区选中解压后的资料目录，建个会话，把 `task.txt` 的内容粘贴进去。

你应该看到模型真的去读了那几份文件，而不是凭“已付款未开通”几个字编通用建议。结果要能确认三件事：ORD-10086 已支付未退款；ACCT-017 的权益仍未生效；最近开通任务超时、观察时点没有在途任务。如果它拿 ACCT-018 的成功状态说工单解决了，就是关联错了；如果它说“已经修好”，却没有任何写入和后续查询记录，就是超出证据了。

**这个练习练的是查资料、做核查、给建议。** 想变成真的企业流程，要把文件入口换成接好的业务查询工具，再按需加上审批后的写入能力。资料包本身没连 CRM、支付或权限系统。

## 从人工到自动，分四步走

1. **人工发起只读核查。** 客服输工单号，拿到报告，自己决定用不用建议。先验证关联准不准、证据全不全、省了多少事。
2. **新工单自动建任务。** 工单系统把可信身份和工单号传给 Harness，不用客服一直开着网页。
3. **审批通过再动手。** 报告挂正式审批，批了才调补开通接口；被拒就停，不能换条工具路径绕过去。
4. **最后才考虑有限自动执行。** 只放范围明确、后果可控、能防重复、结果能验证的动作。身份对不上、数据矛盾、未知错误、超出授权，一律回人工。

企业任务系统要保存“待查询、待审批、已提交、待复查、已完成、需人工”这些状态，进程结束不能丢工单，重复事件不能重复办业务。会话记录能帮你回看它做了什么，但订单和工单的最终状态以业务系统为准。

## 同一套路子能用到哪

链子是一样的：收到请求 → 确认对象 → 查事实 → 对规则 → 提建议或动手 → 验结果 → 留记录。换的只是查什么、能动什么、什么算完成。比如员工申请系统权限、客户说发货了但查不到物流、构建失败、采购到货数量不对、客户投诉同类故障。

判断标准也一样：得跨几个系统查、输入不太统一、结果能用已有系统验证。纯固定计算、单条件判断、没有可靠数据入口的活，不值得上这一整套。

## 试点的时候看什么

先挑一类重复出现的工单，拿一批已知结果的历史样本去验，再决定扩不扩大。别只看回答流不流畅：

- 关联对不对：租户、账号、订单、产品有没有张冠李戴
- 结论能不能追溯：每个关键事实有没有对应的查询结果和时间
- 查不到时停不停：接口失败、资料不够时有没有明确升级，而不是编
- 省没省人工：跟原来查后台、复制资料、写回复花的时间比
- 有没有越权或重复动作：结合业务接口和审计记录查，不能只看回答
- 成本划不划算：模型调用、接口查询、运行环境、人工复核加起来
- 闭环成没成立：权益真的生效了，而不是只生成了一个任务编号

还有数据去向要先弄清：本机装 Harness，不等于数据只留在本机。进到模型上下文里的工单内容和工具结果，都会发往配置的模型端点。先定好哪些字段能进模型、走不走企业网关、返回数据怎么限制。另外官方还提到会话日志上传和遥测开关，用企业资料前去 Web 设置里检查一遍，一个开关关了不代表所有数据传递都关了。[官方数据与部署默认行为](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/apps/cli/reference/README.md#shared-deployment-behavior)

先定一个最小目标：客服输工单号，就能拿到一份对象准确、证据完整、建议清楚的核查报告。这步有价值，再接审批和补开通。每加一项能力，都要能说清它省了哪段人工、靠什么业务结果证明做对了。
