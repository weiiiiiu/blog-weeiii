## 一句话

协议就是两边约定好的"说话方式"：谁先开口、能不能同时说、说完要不要等回复。选错了也能跑，但要么慢、要么费电、要么代码绕弯。

## 例子：一次语音问答

用户对平板说一句话，问"保修多久"，答案从平板播出来。中间走了四种协议，每种只干自己最顺手的那一段：

**第 1 段：平板录音，WebSocket 发文字流。**用户一说话，平板就把语音发往 Spark，ASR 在 Spark 上跑，文字流要实时传过去。WebSocket 像打电话，接通后双方随时能说话，不用每次重新拨号，语音这种一刻不停的流只能走它。HTTP 一问一答，每句话都重新建立连接，扛不住这种持续流。

**第 2 段：Spark 内部，RAG 检索走 HTTP。**ASR 转完文字，mini-rag 收到问题：embedding、Milvus 搜 top20、BM25 搜 top20、RRF 融合、重排取前 5。这一步是"问一次、答一次"，内部服务之间调一下就完事，HTTP 最简单。服务多了、调用频繁了，可以换 gRPC：同样问答，但数据压得更小、速度更快。

**第 3 段：大模型生成，SSE 一字字推回来。**32B 模型开始生成答案，温度 0.2。答案不是等全写完再发，而是一字字推回平板，首字先出来、用户先看到。SSE 是广播喇叭，只能服务端往客户端推，正好对上"生成"这个单向流；它基于普通 HTTP，断线还能自动重连。这段不用 WebSocket，因为平板不需要在这条线上回话。

**第 4 段：TTS 音频流，WebSocket 回传。**CosyVoice2 把答案合成语音，音频流再走 WebSocket 回平板，边收边播。和第 1 段一样，是持续的流、双向都可能说话，所以还是 WebSocket。

## 先分两类

记住两类就够了：

- **问答式**：客户端先问，服务端再答。HTTP、HTTP/2、HTTP/3、gRPC 都是这类。REST 不是协议，是 HTTP 上的一种用法约定（用 GET/POST 加 URL 表示资源）。
- **推送式**：服务端能主动推，不用等客户端问。WebSocket、SSE、长轮询是这类。

## 每个协议一句话

| 协议 | 像什么 | 方向 | 适合 |
|---|---|---|---|
| HTTP/1.1 | 寄信，一问一答 | 客户端 → 服务端 | 查一次数据 |
| HTTP/2 | 同一条马路分多车道 | 客户端 → 服务端 | 网页加载快 |
| HTTP/3 | 换 UDP 修的路，弱网更稳 | 客户端 → 服务端 | 同上，连接更快 |
| WebSocket | 打电话，随时能说 | 双向 | 聊天、语音流、实时协作 |
| SSE | 广播喇叭，只能服务端推 | 服务端 → 客户端 | AI 流式输出、通知、股价 |
| 长轮询 | 反复问"有新消息吗" | 客户端 → 服务端 | 兼容性最好，但费资源，已过时 |
| gRPC | 微服务之间的高速专线 | 客户端 → 服务端 | 服务内部互相调 |
| MQTT | 小区公告栏，订阅了才收到 | 发布 / 订阅 | 物联网、传感器、智能家居 |
| AMQP（RabbitMQ） | 传话筒，活儿丢进队列慢慢取 | 异步 | 服务之间解耦 |
| Kafka | 记账本，消息按顺序写进日志 | 异步 | 日志、埋点、事件流 |
| WebRTC | 点对点直连 | 双向 | 音视频通话、屏幕共享 |
| TCP | 打电话，保证收到、顺序不错 | 底层 | HTTP、WebSocket、gRPC 都跑在它上面 |
| UDP | 喊话，丢了就丢了 | 底层 | 视频通话、游戏、DNS、HTTP/3 |

## 怎么选

| 场景 | 选什么 | 为什么 |
|---|---|---|
| 查一次数据 | HTTP/REST | 简单，够用 |
| AI 一字字吐出来 | SSE | 服务端单向推，断线自动重连 |
| 双向实时（聊天、语音流） | WebSocket | 双方随时说话 |
| 服务内部互相调 | gRPC | 快，体积小 |
| 设备上报、智能家居 | MQTT | 轻量省电 |
| 服务之间异步干活 | 队列（RabbitMQ/Kafka） | 不用同时在线 |
| 音视频通话 | WebRTC | 点对点，延迟低 |

## 一个容易搞混的点

SSE 和 WebSocket 不是谁替代谁：答案生成是单向流，用 SSE；语音来回传是双向流，用 WebSocket。看方向选，不看名气选。
